# 风格判断与方案分级

SKILL.md 的「风格判断」和「方案分级」是压缩版；这里是判断依据。读完后仍以具体页面为准，不套模板。

## 一、识别页面类型

先看路由名、主要内容块和用户动作，归到最接近的一类（可以是组合，以主类为准）：

| 页面类型 | 识别信号 |
| --- | --- |
| 数据后台 / 工具型 | 表格、图表、筛选器、侧边导航、KPI 卡片、批量操作 |
| 营销落地页 / 产品展示 | Hero、特性区块、定价、客户 logo、CTA 按钮 |
| 表单 / 流程 | 多字段输入、步骤条、保存/取消、校验提示 |
| 内容阅读 / 文档 | 长文本、目录、代码块、标题层级 |
| AI 对话 / 生成界面 | 输入框 + 消息流、流式输出、生成中状态、模型选择 |

## 二、每类的风格基调

| 页面类型 | 基调 | 优先手段 | 不要做 |
| --- | --- | --- | --- |
| 数据后台 / 工具型 | 克制、密度适中、功能优先 | 统一栅格与 4/8pt 间距；弱化边框改用背景层次；主操作只有一个高亮；状态色只用于状态 | 渐变、装饰背景、持续动效、每张卡片都有阴影 |
| 营销落地页 | 有节奏、有焦点、留白大 | 清晰的标题字阶（至少 3 级）；每屏一个视觉焦点；Bento 或分栏做分组；数字/文本动效点到为止 | 密集表格式排版；每屏都动；文字压在复杂背景上 |
| 表单 / 流程 | 清晰、分步、低认知负担 | 按业务分组成卡片或区块；单列优先；主按钮唯一且靠近完成点；即时校验与错误定位 | 多列并排塞满；装饰元素；主次按钮同权重 |
| 内容阅读 | 可读性优先 | 行宽 60–75 字符；行高 ≥1.6；标题层级与正文对比明确；代码块与引用有独立样式 | 窄行距；花哨字体；正文宽度撑满大屏 |
| AI 对话 / 生成 | 反馈明确、状态可见 | 空闲 / 生成中 / 完成 / 出错四种状态分明；输入区有焦点态；光效只在生成中出现 | 背景一直在动；用动画代替状态文字；生成中无法中断 |

## 三、读出项目当前风格

从代码里找这些信号，用一句话总结"当前风格"，并判断它内部是否一致：

- 字体：系统字体 / 单一无衬线 / 衬线标题 / 等宽
- 圆角：0 / 小（4–6px）/ 中（8–12px）/ 大（16px+）/ 全圆
- 颜色：是否有 token（CSS 变量、`@theme`、Tailwind 配置）；主色数量；灰阶是否统一
- 阴影与边框：靠边框分层还是靠阴影分层；是否混用
- 间距：是否按固定刻度；同类元素间距是否一致
- 组件库：一套还是多套；版本是否一致

"不一致"本身就是最常见的设计感杀手：同一页面出现三种圆角、两种灰、既有边框卡又有阴影卡。优化时先统一，再谈别的。

## 四、方案分级

| 等级 | 含义 | 触发条件 | 一句话模式下的动作 |
| --- | --- | --- | --- |
| A 排版调优 | 不加依赖，只调层级、间距、分组、对齐、按钮权重、统一 token | 默认 | 直接做 |
| B 框架内升级 | 沿用现有库，引入 1–2 个免费组件补足缺口 | A 做完仍有明确缺口（如缺数据表、缺状态反馈、缺视觉焦点） | 新增运行时依赖 ≤1 个、免费、兼容现有栈 → 直接做；否则说明后等确认 |
| C 换方向建议 | 现有框架不足以支撑目标，给出迁移方向与路径 | 下列信号 ≥2 条 | 先完成现有框架内的 A 级安全改动，再给建议；迁移本身不执行，等用户定方向 |

### C 级触发信号

1. 没有设计 token：颜色、间距、字号散落在组件里硬编码，改一处要改几十处。
2. 多套组件库混用或同一库多版本并存，风格无法统一。
3. 所用 UI 库已停止维护，或与当前框架版本不兼容（如 React 19 下大量 peer 警告）。
4. 深浅色、响应式、键盘可访问性等基础能力现有库不支持，补丁成本明显高于迁移。
5. 用户明确表示愿意换框架或重做。

只满足 1 条时，不建议换，用 A/B 修。

### C 级建议怎么写

- 一句判断：说明命中了哪几条信号，以及为什么 A/B 修不划算。
- 推荐方向：基于项目现有栈选兼容面最广的底座。React 项目若目标是接入路由表中的来源，shadcn/ui + Tailwind 是其中多数来源的共同前提；Vue 项目优先 Vue 生态且先核实各来源是否有 Vue 版本；不推荐与现有框架不兼容的方案。
- 迁移路径：先建 token（颜色 / 间距 / 字号 / 圆角）→ 再换基础组件（按钮、输入、卡片）→ 按页面逐步迁移，老页面不动。
- 本轮仍交付：在现有框架内能安全做的 A 级改动。C 级"停下来问"问的是迁移方向，不是 A 级改动——A 级改动不需要等确认，先做，再把建议和已做改动一起交给用户。

## 五、一句话模式的边界

用户只说"优化这个页面"时，自主完成诊断 → 风格判断 → 分级 → A/B 实施 → 验证 → 报告。只在以下情况停下来问：

- 页面用途无法从代码和截图判断，且两种判断会导致相反的改法。
- B 级需要新增依赖超过上面的阈值。
- 判断为 C 级：先完成 A 级安全改动，再给建议，由用户决定是否迁移；不要因为判定为 C 就一个文件都不改。
- 改动会触及用户在项目规则里标注为"不要动"的区域。

报告里始终包含「风格判断」与「方案等级」各一行，让用户知道技能为什么这样做。
